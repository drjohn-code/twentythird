# I18N.md — TwentyThird Internationalization

> Multi-language support across marketing, auth, onboarding, the Room, settings, the
> invite landing, transactional email, and AI-generated analyst output. This file is the
> map; read it before touching anything locale-related.

---

## Library & the no-URL-prefix decision

`next-intl` (v3) in its **"without i18n routing"** mode — the locale comes from the DB/cookie,
not a `/de/...` URL segment. Wired via `createNextIntlPlugin("./i18n/request.ts")` in
`next.config.ts`; the provider is mounted once in `app/layout.tsx`
(`<NextIntlClientProvider>`), wrapping both the marketing and `(room)` trees.

**Why no prefix:** the app is mostly a private dashboard with auth `next=` params, Stripe
return URLs, signed invite tokens, and email deep links — all of which become locale-fragile
under prefix routing. Cookie/DB locale integrates cleanly with the existing route groups and
`MarketingChrome` prefix logic.

**SEO tradeoff:** marketing pages lose static caching and per-language URLs. If localized
marketing URLs are wanted later, `next-intl` supports adding a `[locale]` segment *without
rewriting the message layer* — the catalogs and components stay as-is. Don't pre-build it.

## Supported locales & adding one

The set, autonyms, scripts, and the country→locale map live in **one file**:
`lib/i18n/locales.ts`. The 24 official EU languages + Norwegian (`nb`), Ukrainian (`uk`),
Icelandic (`is`). All are LTR — **no RTL/bidi work exists**; adding Arabic/Hebrew later would
require it.

**To add a language:** add one row to `LOCALES` in `lib/i18n/locales.ts`, add its country
codes to `COUNTRY_TO_LOCALE`, and produce a `messages/<code>.json` catalog (run the draft
script). The `Locale` union type, the switcher menu, Accept-Language negotiation, and the
catalog loader all derive from that one row.

## Locale resolution order

Evaluated server-side per request in `lib/i18n/locale.ts` `getActiveLocale()`:

1. **Signed-in →** `users_meta.locale` (if set & supported) — the durable source of truth.
2. else **`NEXT_LOCALE` cookie** (if supported) — source of truth for anonymous visitors.
3. else **IP geolocation** — the middleware (`middleware.ts`) reads `x-vercel-ip-country`
   (Vercel) → `COUNTRY_TO_LOCALE` on first visit and writes the cookie (forwarded on the
   request so the first render already sees it). A dev escape hatch `?__locale=xx` forces it.
4. else **Accept-Language** negotiation (`lib/i18n/negotiate.ts`, edge-safe).
5. else **`DEFAULT_LOCALE`** (`en`).

Locale is resolved on the server, so `<html lang>` is correct on first paint (no flash shim,
unlike theme). An explicitly-requested locale (`getTranslations({locale})`) takes precedence
over the request resolution — this is how email renders in the recipient's language and how
metadata can be localized (`i18n/request.ts` honors the passed `locale`).

### Lifecycle (anonymous → authenticated)
- Middleware sets `NEXT_LOCALE` from IP/header on first visit.
- The toolbar `<LocaleSwitcher>` writes cookie (+ DB if signed in) via the `setUserLocale`
  server action (`lib/i18n/actions.ts`), then `router.refresh()`.
- On first sign-in/sign-up (and the OAuth/confirm callback), `syncLocaleOnAuth()` copies the
  cookie into `users_meta.locale` if the stored value is still the default.
- **Onboarding** name/age step has an explicit language `<Select>`; it writes
  `users_meta.locale` + cookie and is authoritative thereafter.
- **Settings → Account** has a live language dropdown (`LocaleSelectField`) → writes via
  `/api/settings/account` (`field: "locale"`, sets cookie + DB) → fires the save strip +
  `router.refresh()`.

## Two classes of content (critical)

**Class A — static product copy.** Marketing, nav, buttons, labels, settings, depth/reading
copy, block subtitles/definitions, catchup/intake/relationship questions, email shell labels,
safety copy. → Lives in **message catalogs** (`messages/*.json`), fully translated, resolved
at render via `getTranslations` (server) / `useTranslations` (client).

**Class B — user data & AI-generated analysis.** Intake/catchup answers, session transcripts,
AI-written readings/ledes/summaries/reports, the analyst's replies. → Generated in the user's
**active locale at write time** (every prompt builder takes `locale`; see below) and **stored
as-is**. **Class B is never retranslated on a locale change** — switching from German to French
leaves past German readings German; new analysis is French. (Optional future affordance:
"regenerate in current language" — not built.)

**The `lib/` split:** `lib/blocks.ts`, `lib/catchup-questions.ts`,
`lib/relationship-intake-questions.ts`, `lib/onboarding/steps.ts`, `lib/intake/answers.ts`,
`lib/connections.ts` keep their **English** strings — these feed AI prompts, the case-file
detail cache, and answer validation (Class-B context / stable identifiers). The **rendered UI**
resolves the display string from the catalog by the stable id (slug / question key / role
value). Don't remove the English from these libs.

**`handle_new_user()` seeds 12 thin English `block_readings`** — intentionally left English.
They are ephemeral placeholders, superseded within minutes by the post-intake
`initial_readings` AI pipeline, which by then knows the user's locale and writes Class-B
content in it. The trigger cannot see the request cookie, so it can't be locale-aware.

## Fonts (no new typeface)

Three families cover every supported script. Subsets added in `app/layout.tsx`:
- **Inter, JetBrains Mono, Source Serif 4:** `latin`, `latin-ext`, `cyrillic`, `cyrillic-ext`,
  `greek` (covers Greek `el`, Cyrillic `bg`/`uk`, and Latin-ext diacritics).
- **Instrument Serif** (the display face): `latin`, `latin-ext` only — it has **no
  Cyrillic/Greek** on Google Fonts. Rather than add a face, its CSS fallback chain in

  Verified: no tofu in Greek/Cyrillic headlines/body; Polish/Czech diacritics render correctly.

## Translation workflow

English (`messages/en.json`) is the source of truth. Every other catalog is **deep-merged over
English per key** in `i18n/request.ts` — a missing/empty key falls back to English, never
crashes (dev logs a warning).

**Glossary:** `messages/_glossary.md` — (a) do-not-translate (TwentyThird, 23, CognitiveLab,
WelloWork AB, proper names, Fig. NN, Stripe, prices), (b) controlled product terms (Room,
Consulting Room, the analyst, Case File, reading, Reading Depth, Catchup, connection, …) with
one locked translation per language. Fed to the draft generator and every review pass.

**Machine drafts:** `scripts/i18n/draft-translations.ts` translates a whole namespace at a time
(chunked per sub-object for large ones like `marketing`/`intake` so calls never truncate; a
failed sub-chunk falls back to English for just that key). It routes through `lib/ai/router.ts`
via the `i18n_draft` task (model overridable with `AI_MODEL_I18N_DRAFT`) — **no model name or
URL lives outside the router**. Dev/CI only; never a request-time call.

Each non-English catalog carries `"_meta": { "status": "machine-draft", "reviewed": false }`.
Review status:
- Set `_meta.reviewed: true` to **lock the whole file** — re-runs skip it.
- Or list dot-paths in `_meta.lockedKeys` (e.g. `["nav.signIn"]`) to lock individual strings
  while re-drafting the rest. Locked values survive re-runs.

**Run it** (server-only must resolve to empty in plain Node → react-server condition; env from
`.env.local`):

```
node --conditions=react-server --env-file=.env.local --import tsx \
  scripts/i18n/draft-translations.ts [locale ...]
```

No locale args → all non-English locales. After writing new catalog files, **restart the dev
server** — Next's webpack dynamic-import context for `messages/*.json` is built once and won't
pick up new files until a restart (a non-issue in production builds).

> Quality, not gatekeeping: the English fallback is a safety net for a genuinely missing key,
> not an expectation that translations are poor. Ship the machine drafts; the owner reviews and
> sends feedback only where a string reads wrong. A consistent fully-translated experience beats
> a partially-English one.

## Email (recipient's language)

Templates in `lib/emails/*.ts` are pure-ish functions that now take a `locale` and resolve copy
via `getTranslations({ locale, namespace: "email" })`. The shared `brandEmailShell` takes an
optional `chrome` object for its localized strings (`orWord`, `fallbackPreamble`,
`attendingInstitution`, `tagline`, `automatedFooter`); the institution name
(`CognitiveLab, WelloWork AB`) and `Fig. NN` stay fixed. **`ATTENDING INSTITUTION` is a label —
it is localized.**

**`italicPhrase` invariant:** `brandEmailShell` throws unless `title.italicPhrase` is an exact
substring of `title.text`. For each locale the title/phrase pair is translated *together* so the
phrase stays a substring. **Belt & braces:** every template checks
`titleText.includes(italicPhrase)` and falls back to the **English** pair for that one email if
it fails — a single English subject is better than a thrown send.

**Recipient locale** (`lib/emails/locale.ts` `localeForUser`): logged-in recipient →
`users_meta.locale`; **invite → the inviter's locale** (the note is in the inviter's language;
the invite landing lets the recipient switch); connection-ended → the recipient party's locale.
The Supabase Auth password-reset email is rendered by Supabase, not us — out of scope.

**Dev preview:** `/api/dev/preview-email?kind=<kind>&locale=<code>` renders any template in any
locale (NODE_ENV-gated).

## AI output & safety

- Every analyst prompt builder in `lib/ai/prompts/*` takes `locale`; `ANALYST_VOICE` is
  followed by `analystLocaleDirective(locale)` (respond entirely in the language, keep the voice
  and every term of art, keep italics-as-voice). Request-context routes resolve locale via
  `getActiveLocale()`; internal/scheduled routes use the target user's `localeForUser`.
- The **safety classifier** (`lib/ai/prompts/safety-classify.ts`) is language-agnostic: it
  classifies input in any language on the same severity scale, and the stored `excerpt` stays in
  the user's original language (the clinician needs source words). Severities / `safety_flags`
  shape unchanged; the fail-safe `classifier_failed` low flag is unchanged.
- The safety **surface** ships translated: `SafetyResponse`, the `RoomFooter` crisis line, and
  the catchup `professional_care` response all read from the `safety.*` catalog. Crisis numbers
  (988, 116 123, 112) stay literal.

## Conventions

- ICU MessageFormat for every count (`{n, plural, one {…} few {…} many {…} other {…}}`) —
  Slavic/Baltic plural categories are required, never concatenate. Verified correct for Polish.
- Locale-aware dates/relative-times/counts via `next-intl`'s formatter where they're real user
  data. **Stylized clinical figures stay as authored** (`37×`, `.72`, `~14 wks`, `n = 2,418`) —
  they're visual grammar, not user data. Pure ISO/mono dates stay ISO (locale-neutral, clinical).
- Pricing literals (`23.23`, `11.11`) stay literal in the JSX of the confirm pages; only the
  surrounding sentence is localized — never the numeral, never on a button.

## Resuming / completing translations

The English catalog is complete. Non-English catalogs are produced by
`scripts/i18n/draft-translations.ts`. To fill any keys that are missing from a locale (e.g.
newly added keys, or keys dropped when an earlier run hit a transient error / ran out of
OpenRouter credit), run the **incremental** pass — it translates only the missing keys per
locale and merges them in, leaving existing translations untouched:

```
node --conditions=react-server --env-file=.env.local --import tsx \
  scripts/i18n/draft-translations.ts --missing
```

Then restart the dev server (webpack picks up changed catalog files) and `npm run build`.
`translateNamespace` retries with backoff, so single-call namespaces survive transient
rate-limits. Keep concurrency modest (run sequentially or in a few groups) to avoid 429s.
